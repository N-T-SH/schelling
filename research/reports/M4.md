# M4 Real training: report

**Result: the M4 done-criterion is not met.** The trained ModernBERT-base is worse than the item-mean baseline B1 on Twin-2K-500 `heldout_person` validation NLL, by a margin that is consistent across all three question types. It is well calibrated, not mode-collapsed and order-invariant, so the shortfall is accuracy, and it comes from a run that was far smaller than a real training run (see "What this run is"). This is a clean negative result at this budget, not evidence that the design cannot work.

All numbers: validation partition only, seed 0, full evaluation by the unchanged harness at code revision c15a922 with a clean tree. The test partition was never read. Goldens are frozen (see below).

## What this run is

- Model: ModernBERT-base with the lower 14 of 22 layers and the embeddings frozen, trained with person attributes only (no history), random option permutation, study-temperature sampling (square root of study size), AdamW with a cosine schedule. Config: `configs/base.yaml` with 2,400 steps of batch 32, which is 76,800 example presentations, about seven per cent of one pass over the 1,095,076 training rows.
- Why so small: the Mac's GPU trains at roughly 4 seconds per step of 32 examples (A12; benchmark in `research/STATE.md`). One epoch would take about two days of wall clock, and the evaluation of the full validation partition alone took close to two hours because the harness runs the model on CPU.
- Single seed, one config, no tuning on validation beyond keeping the best checkpoint (the last one).

## Why it falls short (hypotheses, not verified)

1. **Too little training.** Validation NLL was still improving when the cosine schedule reached zero; the last two checks differ only because the learning rate had decayed. The item marginals that B1 gets exactly from over a million rows are being learned from text by a network that saw each of the roughly 590 items about 130 times.
2. **A text-in architecture pays to re-learn item identity.** B1 knows the item exactly; the model must infer it from the question text on every example, and every example costs a full encoder pass over a long context (about 175 tokens on average), which is what makes training slow.
3. **Frozen lower layers and attribute-only context** limit how much person information is used; B3 shows attributes add very little over B1 (decision: conditioning on a person's other answers is campaign C01).

## Deviations and choices to review

- Psych-101 is in the training mix through the sampler but is not part of the bar (decision 0001).
- I froze 14 layers for speed (a compute decision, not a modelling one) and capped contexts at 256 tokens; the compact person text drops parenthetical asides.
- The evaluation ran the model on CPU: the harness loads models without moving them to the GPU, so `efficiency.p50_ms` is a CPU figure and the evaluation was much slower than necessary. The latency target in the spec (50 ms on one GPU) is therefore not measured. Fixing it needs a one-line change in `infer/baseline_adapter.py` plus a device label in the sealed `eval/efficiency.py` (an eval-change).
- `torch` and LightGBM cannot share a process on macOS, so B3 tests run in a separate interpreter (M3 report).
- Golden metrics frozen: `tests/golden/metrics.json` from the fixture benchmark; the regression test passes (marked slow, not in CI).
- Tests-first held this time: losses, calibration, sampler, config and the training integration tests (50-step run, bitwise-identical rerun = A13 verified, CLI train then eval) were written before the trainer.

## Assumptions

A13 verified for training: two 50-step CPU runs with the same seed give identical metrics (`tests/integration/test_train.py`). Evidence added to `research/ASSUMPTIONS.md`.

## Options for the next step (your decision; this is the checkpoint)

1. **Redesign for efficiency, via a decision record.** The goal is realistic populations, and the current design is a working hypothesis (AGENTS.md). A two-tower design encodes each question and each person separately and combines them cheaply, so a question's representation is computed once per item rather than once per example. That would let me train on all one million-plus rows in minutes and add a learned item prior, making "at least as good as B1" the starting point instead of the target. I recommend this.
2. **Spend more compute on the current design:** a rented GPU (needs your approval, as paid compute) for a full unfrozen epoch or more. Expected to close part of the gap; no guarantee it beats B1.
3. **Accept the gap for now** and move to campaign C01 (conditioning on other answers) with this model, knowing it starts behind B1.
